# P9: the disc menus on the HPS (host B) -- the plan

**Status: ✅ MERGED (PR fj#38, 2026-10-03), ✅ HW-CONFIRMED on the three captured discs (M0-M3b).** M0 (the
census), M1 (the engine on the PC), M2 (the fabric: NAV_PLAY, the host rows, the gate, the hand-over,
the sound one-shot, the video window), M3 (the engine in the UMD Main: the image reader, PLAYLIST.UMD,
the host-row logic, the menu host, the glue, the sounds; three rig sessions on Family Guy, then Akira
and Austin Powers 2 matching their captures) and M3b (Disc Menus On / Off) are built; the last fit
SEED 3 PASS 90.61 / 89.90, 39,125 ALM (93 %). Decisions P9-1..P9-6 in §7. **M4 ✅ MERGED (PR fj#39), ✅ HW-CONFIRMED** (§3.3 "M4", §4): every library disc (88 images) reaches its feature through its own
menus or startup chain on host C; ten engine rules and one fabric gap (a menu over a stopped player) found
and fixed; the rig sample matches; fit SEED 9 PASS; ✅ on the rig.

**Emulation, not approximation** (the maintainer asked, 2026-10-01): the engine runs each disc's own
compiled scripts in a VM that executes the bytecode as written; no menu logic is written per disc.
The PSP captures specify the other half -- Sony's player firmware, the native functions and rules
the scripts call into (the startup choice, `play()`'s modes, resume, animation time units and
easing, the menu button, loop seams) -- which no one has documented and JPCSP mostly stubs. The 2026-09-25 design is `docs/menus.md`; this note supersedes its
host-A parts and its milestones, and keeps its oracle ranking (§2 there) and its fabric contract
(§4 there) as amended below. The goal (the maintainer, 2026-10-01): **the "authentic UMD
experience"** -- the disc's own startup chain, menus, scene select, set-up and resume -- and with it
the last fabric logic chunk of the core.

**The stock-Main rule holds** (`area_plan.md` §8 A5): with stock Main, or with the UMD Main on a disc
the engine refuses, the core plays the longest playlist exactly as today. Menus are a UMD Main
feature.

**The scripts** (`rco_census.py --disasm`, six discs): `movieplayer.play` takes **raw MPEG stream
ids**. Family Guy: `play(0, 1, 15, 1, 0xE000, 0xBD00, 1, 1, 0)` = pause mode 0, menu mode 1,
playlist 15, chapter 1, video stream 0xE0, audio 0xBD + substream 0, audio on, subtitle 1,
subtitle off. 111 of 130 calls pass 9 or 10 arguments. `setInterval` periods are 100-1,250
(milliseconds). `changeResource` names the next file outright (`'EN000001'`, `'EN100000'`).

**JPCSP** (the only open implementation, `docs/menus.md` §2.2) is a partial prototype: its RCO and
VSMX parsing are reliable, its behaviour is not. `play()` honours only the playlist; `stop()` /
`resume()` are flags; `setInterval` fires once; `onCancel` / `onExit` / `onContinuePlay` never
fire; Fade / Rotate / SlideOut / Lock do nothing; sounds never play; numbers are float32; a
native call with no return value pushes nothing (the likely cause of its jpcsp#445 crash). Its
startup list (`100000`, `000000`, `110000`, `010000`) does not contain `EN000001`, the lowest file
on 49 of our discs. **It is a format reference and a tiebreaker, never the golden.**

## 3. The design

### 3.1 Where each part runs

| part | where | built in |
|---|---|---|
| RCO loader, VSMX VM, scene graph, animation, renderer, VAG decode, the player-API shim | **the UMD Main** (`main/support/umd/menu/`, portable C) | M1 (on the PC: host C), M3 (on the HPS) |

### 3.2 The fabric (M2): the last logic chunk

1. **Playlist play** (`umd_reader`): today the reader chooses the longest playlist at the mount
   and its `NAV_SEEK` / `NAV_CHAP` work inside it. A menu plays any playlist from a chapter
   (warnings, motion-menu loops, trailers, the feature from a chapter). The minimal change is a
   `NAV_PLAY p` that replaces "the longest" with playlist `p` and re-runs the existing walk -- items,
   IN / OUT, marks, `pl_dur` all follow -- then a `NAV_SEEK` to the chapter's mark. P6b2 landed at
   2x its plan: measured with `tools/synth_unit.sh` before a number is promised.
   **As built (2026-10-01):** one command, `NAV_PLAY (pl, item, pts)`, not a play then a seek (no
   flash of the playlist's first picture before the chapter): the table walk with `pl` forced,
   then the seek's own item walk (`transport.md` §2.4 has the contract). An item past the
   playlist's last plays it from its first (`NE_ITEM`); an empty playlist lands on its end. The
   chapter's `(item, pts)` comes from the engine (it parses PLAYLIST.UMD on the HPS).
   `run_umd_reader.sh --red`: syn_nav (a trailer sharing the feature's clip, an empty playlist,
   back to the feature) and every disc image (another playlist chosen by the seed, a chapter
   query and a seek on it, the clamp, the feature again), P1-P8. The bench found one bug on the
   way: the output pipe flushed on a seek only, so a PLAY delivered the old phase's bytes (P4).
   **Area** (`tools/synth_unit.sh umd_reader`, `nav_pl` a port so nothing folds): 5,457 -> 5,620
   combinational ALUTs (+163), 3,908 -> 3,925 registers (+17): ~100 ALM, against P6b2's 2x. In
   `emu` it is free until `player_ctl` drives `nav_pl` (tied to 0 today).
2. **Host rows on `umd_host`** (EXT_BUS, `hps_host.md` §2): commands from the engine (play
   p / chapter / video / audio / subtitle ids, stop, pause, resume, the menu gate), status back
   (state, playlist, chapter, time, the current streams), an event FIFO (playlist end, chapter
   change, mark reached). `player_ctl` executes them with the logic it already has.
   **As built (2026-10-01):** `umd_host` + `tools/host_layout.py`, rows appended (PROTO 1 kept,
   NWORDS 13 -> 38 the capability), once-only by seq with an echo, the levels cleared when the
   heartbeat stops, the event FIFO read by count (`hps_host.md` §2 "P9's rows, as built"). Two new
   `player_ctl` codes: **13 PLAYLIST** (a Go To through `NAV_PLAY`, from any state -- a menu plays
   from STOP --, ending trick play; a playlist that does not exist, or a gesture / seek in flight,
   is BAD) and **14 SUB_SET** (the subtitles set outright). `run_umd_host.sh --red` (H7-H17),
   `run_player_ctl.sh --red` (P52-P61: the model scores every PLAYLIST's port request against its
   key and playlist; the mock lands a missing item on item 0 as the reader does).
3. **The menu gate**: while the engine owns the screen, the J1 buttons go to the engine (the
   UMD Main reads them through its host rows), `player_ctl` ignores them, the transport HUD is
   hidden (the PSP shows no HUD over its menus). The **UMD Menu** J1 button (bit 11, idle since
   P6b6) is the engine's `onMenu`.
   **As built (2026-10-01):** the gate is the host's `grab` mask (joystick bit order, D-pad Up /
   Down included -- the keyboard's arrows too, `kbd_map`), not one bit: every press goes to
   `umd_host`, the grabbed ones become KEY events and never reach the transport; so the UMD Menu
   button in playback (the PSP's square: the maintainer's capture, §2) is the same mechanism with
   only that bit grabbed. `menu` hides the transport HUD and makes STOP black instead of the idle
   wave (a menu page over a stopped title). Pinned by `check_emu_wiring.py`.
4. **`ui`: the plane hand-over** (`hps_host.md` §3.4): no subtitle flips while the host owns the
   plane; a flush under `ui` leaves the page up. Its own `run_overlay.sh` arms.
   **As built (2026-10-01):** in `sub_flip` (`hps_host.md` §3.4 "As built"): units are not queued
   under `ui` (the demux's subtitle output off), either edge flushes; benched by
   `bench/umd/sub_flip_tb.sv` in `run_plane.sh --red` (U1-U6), not `run_overlay.sh`.
5. **The PCM one-shot** (P9-3): a DDR3 buffer of 16-bit PCM (the decoded VAG, mono or stereo, its
   rate converted by the UMD Main to 48 kHz), a start / length / trigger on the host rows, read on
   ram2 and mixed with `aud_out`'s output (saturating). ~200 ALM (`menus.md` §4 item 4).
   **As built (2026-10-01):** `umd/pcm_shot.sv`. The region: core word `0x0660_0000` (HPS
   `0x3300_0000`), 2^20 words = **8 MB**, the reader's address wrapping inside it whatever the host
   sends; mono 4 samples / stereo 2 frames a 64-bit word, little-endian from bit 0. Its own 48 kHz
   tick (the film's stops in pause / stop, when menus play their sounds); a trigger replaces the
   sound playing at once (a generation per burst drops the old one's words), len 0 stops it. On
   ram2 the LOWEST reader, behind a second `rd_merge2` after the video and the plane.
   `run_pcm_shot.sh --red` (S1-S8, a slow DDR3 model, a trigger in a burst's flight).
   **Sizing, measured** (the library's 115 sound channels, `rco_census` walk): the largest channel
   275 KB of VAG (~480K samples), rates 16-48 kHz; at 48 kHz stereo 16-bit the worst ~4 MB. The
   format's per-channel size is a u32: **a sound past 8 MB once resampled is the HPS's to refuse
   (a log line)**, listed in `spec_hardening.md` -- ✅ the 8 MB cap taken by the maintainer (2026-10-02).

6. **The video window** (P9-5): `disp_reader` shows the picture scaled by any factor in each
   axis (the 854 x 480 movie space's `setSize` / `setPos`, mapped to the raster) at a position,
   black around it, the menu plane over it. It generalises S2's walkers (Letterbox's vertical
   DDA, Crop's horizontal one, `analog.md` §3) from fixed ratios to a programmed step and origin,
   2-tap in each axis. Downscales to 29 % alias without a prefilter: whether a box prefilter is
   needed is judged on the rig against the PSP (the PSP itself scales its 720 x 480 video to
   480 x 272 for every window, so its own windows are soft). The window's geometry is
   quasi-static, latched once a field like Analog Aspect.
   **The design (2026-10-02, before the RTL):**
   - *Geometry.* A destination rectangle on the raster {dx, dy, dw, dh} in pixels / frame lines
     and the source the whole picture; steps hs = pw / dw, vs = ph / dh in Q16, computed by the
     UMD Main (no divider in the fabric) and sent with the rectangle as a HOST_WR group, once-only
     by seq like the flip, latched at a frame's set-up (480i: a field's). `win` off = today's path,
     unchanged (every existing arm keeps its golden).
   - *Vertical.* Under `win` both rasters take the 480i path's walker (a source line s and a
     weight of s + 1), generalised from fixed sixths to a Q16 accumulator stepping vs per output
     line, starting at (dy's offset). 480p walks frame lines (a field store: its kept field only,
     the single-field Bob's rule -- a window is small; weave would comb at a fraction of the
     height); 480i walks field lines of the raster's parity as Fit does.
   - *The ring.* A downscale skips lines (vs up to 1 / 0.29 = 3.4), so slot = s & 3 can land the
     next pair on a slot being read. Slots are allocated in FETCH order (a 2-bit counter): the
     walker keeps the slot of s and of s + 1 with the line numbers. Two fetches a line at most (the
     480i path's rate, already in budget).
   - *Horizontal.* Crop's two taps generalised: t0 = X >> 16, the weight X[15:12] (sixteenths,
     shift-and-add like the quarters, no multiplier) with X stepping hs per pixel from dx. The
     even / odd split buffers already give any adjacent pair.
   - *Outside the window* black (de 0), so the menu plane over it shows its frame art.
   - *Quality.* 2-tap bilinear: a downscale below 50 % aliases (the PSP's own windows are soft:
     it scales 720 x 480 to 480 x 272 first). A box prefilter is judged on the rig against the
     captures; not built first.
   - *Bench.* `run_disp_reader.sh` gains window arms (W1..): a golden from `tools/disp_golden.py`
     (the same fixed-point bilinear in Python, bounded against float and PIL as plane_golden does),
     480p and 480i, a field store, the extremes (29 % and 98 %, a window at the raster's edge, one
     pixel), and `win` off bit-exact to today.
   **As built (2026-10-02):** as designed, with these specifics.
   - The geometry is a LEVEL in HOST_WR (13 words: `win` {seq, on}, the rectangle, Q10.16 steps
     and starts), written in place: `disp_reader` latches it once a frame (480p line 522, 480i
     field lines 259 / 260) and never during a HOST_WR (`win_hold`); off when the heartbeat stops.
     HOST_RD's status shows `win` and `win_bad`; `pcm_ack[7:0]` echoes its seq. HOST_WR is 38 words.
   - The position of a step is a MULTIPLY (`x0 + (x - wx) hs`, `y0 + (Y - wy) vs`; 27 MHz has the
     time), not an accumulator: no start-alignment state. Steps Q10.16 reach a one-pixel window of
     a 720-wide picture (720.0) and any upscale.
   - The reader's fetch line went 9 -> 10 bits: a window shows a 720 x 576 picture's rows past 511
     (the non-window paths never fetch past 480).
   - A refused rectangle (empty, or past 720 x 480: the host clips) shows nothing, `win_bad` up.
   - `run_disp_reader.sh`: 8 window cases (50 %, 29 % at an odd origin, 98 % flush to the edges,
     one pixel, a field store's kept field, an upscale of 480 x 272, 720 x 576, a refused one) on
     both rasters, every existing arm unchanged (`win` off bit-exact); RED W1-W11, D2-D5 / I2 / A7
     re-aimed. `run_umd_host.sh` [win] (H18-H20), `check_emu_wiring` + `run_scaffold` W94.

**Measured, items 1-5 (2026-10-01, `tools/synth_unit.sh`, combinational ALUTs / registers, each
module against `main`'s):** `umd_reader` +163 / +17; `umd_host` 241 -> 719 (+478) / 686 -> 1,601
(+915: the event FIFO, the held records, the latched player record, the staging words);

### 3.3 The engine (M1)

- **The API the 84 discs share** (on >= 50 of 84): `movieplayer` (`play`, `stop`, `resume`,
  `getPlayerStatus`, `playListNumber`, `chapterNumber`, `audioNumber`, `subtitleNumber`,
  `subtitleFlag`, `audioLanguageCode`, `subtitleLanguageCode`, `getResumeInfo`,
  `changeResumeInfo`, `playStatus`), `controller` (`getUserData` / `setUserData`, `changeResource`,
  `setFocus`), `resource` (`pagetable`, `animtable`, `texturetable`, `soundtable`), `timer`
  (`setInterval`, `clearInterval`), the callbacks (`onAutoPlay`, `onMenu`, `onPlayListEnd`,
  `onChapter`, `onMark`, `onContinuePlay`, `onExit`, `onChangeResource`) and the objects' methods
  (`open`, `close`, `activate`, `setPos` / `getPos`, `setSize` / `getSize`, `setColor`, `setScale`,
  `animPos`, `animScale`, `animColor`, `texture`). The rest is per disc and measured as it comes.
- **VM rules, defaulted** (not questions; recorded here, changed on the PSP's evidence):
  numbers are float32 (VSMX constants are IEEE singles; the PSP's FPU is single precision);
  **every call pushes a value and every expression opcode pushes exactly one** (`undefined` when
  there is none -- JPCSP's #445 lesson); `setInterval` repeats until cleared; host callbacks run
  with the controller as `this`; a missing property reads `undefined` without creating it.
- **The renderer**: the library's 4 object types (Plane, UButton, Page, Group; no text objects on
  any disc) and its animations, drawn ONCE at the target through the root transform -- the scene's
  854 x 480 space onto the 720 x 480 plane (16:9 anamorphic), or onto 480 x 272 beside a PSP
  capture -- bilinear per image, no second resample. (Planned here first as a 480 x 272 canvas
  resampled to the plane: the discs' own numbers say 854 x 480, M1c below.) It writes the subtitle plane's pixel directly
  (`MENU_PX_PLANE`). Images through a host
  hook: libpng for PNG (linked since A7), and JPEG (5 on Family Guy's main RCO, 51 in 21 RCOs) by
  Imlib2 on the HPS -- the Main links it already, it loads `MiSTer.jpg` -- and libjpeg on the PC.
- **Persistence**: `setUserData` and the resume info to one file per `DISC_ID` beside the UMD
  Main's config.
- **Language**: the RCO prefix matching the MiSTer's language (English unless set), else the
  first prefix present; the startup file is `<prefix>100000.RCO` (§2: the PSP, on three discs).

- **Three engine decisions, taken before the VM (2026-10-02)**:
  - *Memory*: a mark-and-sweep heap of VM values, collected only BETWEEN script runs (an event, a
    timer, a callback: the VM idle), the roots the globals, the live timers and the scene's script
    references. Scripts run per event, seconds apart: a pause is invisible, nothing is collected
    mid-expression, and cycles (objects that reference each other, legal in the scripts) are freed,
    which reference counting would leak. The heap, the operand stack and the call depth each have a
    bound reported and refused loudly (§6), never a crash.
  - *Time*: the engine is driven by `menu_tick(ms)`; `setInterval` periods are milliseconds (M0);
    the animations' `duration` unit is NOT known and is one constant (`MENU_ANIM_UNIT_MS`) set from

## 5. What a user sees

- **UMD Main**: the disc starts as the PSP starts it (warnings, logos, the main menu); the menu
  plays the feature, scene select, set-up; the UMD Menu button returns to the menu.
- **Stock Main**: unchanged -- the longest playlist plays at once (the stock-Main rule).
- **A disc the engine refuses** (an unknown opcode, a bound hit, a missing resource): a message,
  then direct play, as on stock Main. Never a hang.

## 6. Spec maximum

Every table is sized to its field (u16 / u32 counts; the census maxima of §1 are what the library
reaches, not the bound). Runtime structures (operand stack, call depth, heap, timers, the event
FIFO) live in the HPS's RAM; each has a bound that is reported and refused loudly when hit
(a counter in the UMD Main's log and an on-screen message), never a silent stop.

## 8. Risks

- **The PSP is the only oracle.** Without captures the engine follows the scripts' intent and
  JPCSP's reading, and timing is a guess.
- **Seamless motion-menu loops**: a playlist restart through `NAV_PLAY` is a seek; a visible gap at
  each loop is likely in v1. Measured on the rig against the PSP.
- **Area**: P6b2 landed at 2x; `NAV_PLAY` is measured before the rows are sized.
- **The UMD Main follows upstream Main**: the fork's integration is two lines today
  (`main/README.md`); the engine adds a module, not patches.
